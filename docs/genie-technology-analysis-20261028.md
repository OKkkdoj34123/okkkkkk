- 用户日志确认：`legion_exchangeresearch` 请求 `{type, targetType}`，响应是 **`legion_researchresp`**，不是由请求名称简单拼接出的响应名。将来需补请求注册及该响应的命令关联，不改 BON。

## 后续实施应采用的流程（本轮不执行）

1. 首次读取完整科技和余额，保存持久化快照。不能假定账号默认已经点在战士；应找到实际有等级的职业。
2. 若战士未升级，先确定金币/俱乐部资源预算和升级顺序，再按条目升级；每步回读实际等级和余额。该操作会消耗资源，不应隐藏在普通挑战的开始动作里。
3. 按魏→蜀→吴→群，所需职业为法师4→战士1→射手6→战士1。已有目标匹配时不发置换；若存在多套非零科技，须确认双向交换语义，不把一套覆盖另一套。
4. 每次置换先记未决标记，响应后回读源、目标两套等级及资源。超时只读核对，不盲目重试。升级/置换失败时禁止继续用未确认科技挑战。
5. 用户停止、异常或正常完成都进入恢复流程，将用于挑战的科技归回战士1，并回读确认。断网时无法承诺立即恢复；应持久化“待恢复战士科技”状态，重新连接优先恢复，未确认前不报告任务完成。

未验证：有两套非零科技时的置换细节、各账号实际折扣/预算、恢复时钻石不足、断线跨日恢复。基础科技是否已满足全部开启条件，也要逐号读取。
现有代码与用户协议已足以定位以上问题，本轮不需要额外寻找开源实现，更没有发送科技命令。新增四国灯神仍只调整请求中的站位，主C不会继承原最强英雄的等级、装备或鱼灵。

## 证据与实现

2026-11-14的15账号诊断共30次选址，当前位置26_22、地图13、动态建筑99个。静态地图还有225个道路格，旧v3要求道路有动态归属导致零行军。手动日志使用`war_startmarch {target:{x,y}}`和`war_startattackbuilding {buildingId:"x_y"}`，没有提交路径参数；手动日志未收录对应盐场响应，不能用它宣称接口实测已通过。

v4沿静态道路推导附近实时非己方建筑，候选按步数、同距离中立优先、本批已分配人数较少优先、坐标排序。道路只用来推导路线，不作为攻击目标；不穿越中立/敌方建筑。静态道路仅在地图13且当前位置属于该拓扑时启用，显式删除仍阻断。目标建筑继续使用动态类型与归属。

实际地图投影可生成：

| 最终目标 | 候选路径 |
|---|---|
| 26_20 | 26_22 → 25_21 → 25_20 → 26_20 |
| 26_25 | 26_22 → 26_23 → 26_24 → 26_25 |
| 28_24 | 26_22 → 26_23 → 27_23 → 28_24 |

这些是等待服务器确认的候选，不是离线验证过的实服可达集合。每次只发一个最终坐标；明确拒绝时保留错误码、排除该目标，下一次刷新重新选址。沿用每号总尝试上限3次，连接失败也计入，不额外叠加3次行军额度。接受后不再发送其它候选；响应超时先回查，未确认不换目标。

旧v3记录只有在明确为选址失败、布阵已确认、角色新回读为空闲，且没有目标/行军意图/攻击意图/拒绝历史/结算证据时，才允许一次性恢复预算。原记录历史保留；已完成、未决或已发送过行军/攻击的记录不会被重置。无需清除浏览器记录。

后续保持单吕布，不邀请队友、不加速；先逐号行军，再按各自行军时间至少等待120秒并核对实际到达。到达后复核目标归属、读取aB/d基线，攻击一次并等待个人计数和终态证据；收到接受回执或占点归属变化本身不算完成。

- 这是本批观察到的行军意图统计，不是服务器驻军人数、目标容量或跨设备锁。没有增加全局分配系统，也不保证真实活动必然5/5/5；候选变化、拒绝、其他玩家均会影响结果。原有防重和总尝试预算保持。

4. 从现有“盐场诊断”卡片导出本批JSON；分享整份诊断和对应运行时间即可。确认单号流程后，再扩大到原15账号批次。

页面日志保持阶段摘要，JSON自动保留以下事件：

| 事件 | 排查用途 |
|---|---|
| navigation.origin | 当前坐标、动态大本营归属、可选strongholdId交叉核对；缺失不阻断 |
| navigation.snapshot / navigation.candidates | 当前位置、地图编号、道路通行理由、候选顺序、每条候选路径与排除原因 |
| navigation.assignment | 实际选定目标、此前本批其他角色已安排人数、战场/军团范围；明确拒绝和未决结果可结合下列事件核对 |
| march.intent.saved / transport.request / transport.response.matched | 实际发送坐标、请求序号、响应及错误码 |
| march.rejected-or-unknown / march.reconciled | 拒绝与超时区别，是否通过角色状态回查确认 |
| march.arrival.check / march.arrival.check.timeout | 目标与实际位置、角色状态、距行军开始时间 |
| attack.target.recheck / attack.intent.saved / attack.accepted | 到达后归属变化、个人计数基线、攻击请求接受 |
| attack.settlement.check / record.updated | aB/d变化、结算连续核验与最终状态 |

地图包中的`legions`和旧`legionInfo`均只保留id、strongholdId、buildings白名单，不导出其它角色完整资料。沿用最近3批、事件12MiB/30000条上限、丢弃计数和保存失败提示。`sourceBaseline`是本补丁输入基线，不表示用户部署后的实际Git HEAD；诊断标识可区分本次盐场实现。

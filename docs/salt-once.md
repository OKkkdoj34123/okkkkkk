## 安装与恢复

Python 3.9+，无需第三方 Python 包。将 apply_salt_once.py 放在项目根目录或在命令中指定 --project。

```text
python apply_salt_once.py --check
python apply_salt_once.py
node --test test/saltOnce.test.js test/saltOnceTransport.test.js
pnpm run build
pnpm run dev
```

也可在任意目录执行：
```text
python apply_salt_once.py --project "D:\your\xyzw_web_helper_custom"
python apply_salt_once.py --project "D:\your\xyzw_web_helper_custom" --restore
```

--check 只核对版本、冲突和安装状态。默认执行安装，不启动游戏、不调用账号、不提交 Git。
补丁包含全部新增源码、测试和本文；无需联网下载代码。--extract 指定目录可单独导出修改后的文件供审查。
安装时先校验所有文件，再将受影响文件的原始字节备份到项目同级的 <项目名>_salt_once_backups/<时间_随机码>/。
如两处既有文件已被其他修改改变，会整批拒绝安装，避免覆盖后续改动。支持 Windows CRLF 和 UTF-8 BOM。
重复安装不创建重复备份。写入中发生异常会恢复已写入的文件。
--restore 恢复最近一次对应项目的备份；也可 --restore "完整备份目录"。
恢复前检查是否存在安装后的二次修改；如有冲突则拒绝整批恢复，不强制覆盖。删除本补丁新建文件、还原旧文件，保留备份。
备份不包含未改动的仓库文件、账号 Token 或浏览器数据。恢复源码不会清除浏览器盐场记录。

## 执行流程

1. 锁定同源浏览器标签页，冻结本次账号列表，按顺序执行第一阶段。
2. 主连接 legion_getbattlefield 获取 sid/battlefieldId；建立独立盐场连接；等待进场响应及本角色最新快照。
3. 以 battlefieldId + roleCodeId 查记录。同一角色即便以多个 Token 条目导入，也共享防重记录。
4. 布阵 war_teamsetbattleteam、war_setbattleteam，battleTeam 为 {"0":107}。确认空闲和坐标。
5. 在真实 buildingData 图上按六邻接 BFS 找最近候选，接受道路和普通据点，排除己方、大本营和核心。仅穿越已知己方可通行格；最终合法性由服务器确认。
6. 持久化行军意图及目标，发送 war_startmarch。收到接受响应后记录 marchStartedAt，立即关闭盐场及本任务持有的连接，继续下一个账号。
7. 所有账号第一阶段完成后执行第二阶段。从各自行军接受时间起至少120秒，再重新获取入口并回连；核对战场/角色身份、最新角色状态及目标坐标。120秒不是到达依据。
8. 到达要求 state=idle 且 position.x/y 等于保存的目标；仍在行军则轮询，单轮最多60秒。失败后刷新/回连，累计最多3次尝试（包含首次，不是首次加3次）。
9. 攻击前重新核对目标和个人 aB/d 基线，先持久化 attackIntentAt，再发送 war_startattackbuilding(buildingId="x_y")。
10. 攻击成功响应仅表示已接受。连续两次新查询都符合以下任一证据才完成：aB 相比基线增加且角色 idle；或 d 相比基线增加且角色 over。胜负均可完成。
11. 超时/断连/结算证据不足：进入待核验，保留攻击意图，只允许读取核验，不重复发起攻击。成功立即关闭连接，不继续占点或刷战斗。

角色记录包含：战场和角色ID、状态、尝试数、目标、布阵/行军/攻击意图时间、行军接受时间、攻击前后计数、完成时间、错误摘要。
记录保存在当前浏览器同源 localStorage 的 xyzw_salt_once_v1；不会保存 Token。不要清空此记录来“重试”。
刷新/停止后再次点击可根据记录继续核验；页面关闭/电脑休眠时不保证后台执行。跨设备、跨域名记录不共享，不能同时在另一设备或游戏客户端操作同一角色。

## 证据与尚未验证的协议风险

已核对参考源代码：
- 当前仓库 src/stores/legionWarStore.js：主服入口、盐场连接URL、进场和查询。
- 当前仓库 src/utils/legionWar.js：奇偶列六邻接、建筑类型、legionID、aB（刨地）、d（死亡）、idle/march/over 状态。
- gterryd/xyzw-web-helper server/lib/legionWar/saltFieldRunner.js：两条单吕布布阵指令、target:{x,y} 行军、坐标字符串建筑ID攻击。
- 其 server/lib/legionWarWebSocket.js 和 hexUtils.js：命令响应映射、相邻格规则。
- 上传的三份报告用于定位；其中“收到攻击响应就完成”、四次总尝试、并发保持连接均未采用，以本次明确规则为准。

关键限制必须在首次测试中确认：
1. aB 是现有展示代码标注的刨地计数，但公开源码不能证明它在战斗开始还是结算时增加。当前“个人计数增加 + 连续两次终态快照”是保守的工程判据，不等于已取得游戏官方战报协议保证。若实测发现提前变化，必须补充可靠战报/结束通知再用于生产；不得放宽成攻击响应即成功。
2. d 增加且 over 用于死亡结束判据，其刷新时点同样未实战验证。若游戏返回其他终态，本版保持待核验，不猜测。
3. war_getbattlefieldinfo 必须返回显式包含本角色的快照。若只有增量/不同封装，本版失败关闭，不凭缓存判断到达。当前不会伪造字段或使用未证实的结束通知名。
4. 断线后行军是否继续、重新进场是否保留部署、单吕布具体槽位，以及普通道路实际攻击条件，均须测试账号确认。源代码支持该参数链，不等于已在当前服务端测试。
5. 目标选择是客户端候选过滤；动态占领、保护期、地图连接限制仍由服务器裁定。目标失效会刷新、重选或失败，不强攻。
6. 布阵提交响应不明时不反复部署；行军响应不明但查到行军/目标到达，可恢复等待；攻击响应不明永不盲重发。
7. 完成状态表示上述个人结算证据成立，不自动领取奖励；实际参与奖励仍需在游戏内核对。
8. 未实现报名、加速、复活、无限占点、循环攻击；不调用购买或消耗道具指令。

## 首次测试建议（真实账号操作须先获得你的确认）

先只选择1个已报名且拥有吕布的测试号，活动开放时执行；不要同时在游戏内手动行军/攻击。首次不要勾选其他批量任务。
确认后再点击“盐场参与一次”。观察：布阵完成 → 行军目标/时间 → 连接关闭 → 至少120秒后回连 → 实际到达 → 攻击 → 个人计数/终态核验。
用游戏内角色位置、战斗记录和参与奖励核对日志。若待核验，停止，不清缓存、不换设备再次点攻击。
在记录确认无误后，再用2个号验证第一阶段全部完成后才开始攻击；最后扩大到全量账号。
暂停/刷新恢复测试建议在行军阶段做。攻击后断线测试应留待确认正常闭环之后，避免第一场就失去证据。
本次开发与测试没有向任何真实账号发送游戏操作；下一步是经你确认后进行单账号实测。
